# GradSearch 開發歷程與里程碑決策紀錄 (Walkthrough)

這份文件詳細記錄了 GradSearch 專案從初期構想到實際落地的核心歷程。本專案經歷了多個開發迭代，從單純的關鍵字搜尋機器人，進化為具備 RAG (檢索增強生成) 與資料庫自癒 (Auto-Healing) 能力的智慧升學助理。以下統整了開發過程中最重要的 **6 個架構與產品決策**。

---

## 🏗️ 決策 1：初期 MVP Scope 與產品定位定義
- **問題現況／需求**：
  台灣研究所招生資訊（簡章、報名時程、名額）散落於各校官網的 PDF 中，缺乏統一入口，考生查詢與追蹤的成本極高。開發團隊需要一個能快速驗證「整合查詢需求」的 Minimum Viable Product (MVP)。
- **問題拆解方式**：
  將需求拆分為三層：「資料獲取層」、「檢索邏輯層」、「使用者互動介面層」。判斷哪些是首日必備的核心痛點，哪些（如落點分析、論壇交流）可以延後。
- **解方選項**：
  1. 開發完整的 Web 平台（React/Next.js），包含會員登入與討論板。
  2. 開發 iOS/Android 原生 App 並實作考試時程推播。
  3. 開發 LINE Bot，介面極簡化，專注於「精準關鍵字搜尋」與「直接導出簡章連結卡片」。
- **最終行動決策**：
  👉 **選擇選項 3 (LINE Bot)**。
  **為何選它：** 台灣學生對 LINE 的黏著度極高，零下載門檻能瞬間獲取第一批測試使用者；LINE 的 Flex Message 已能滿足結構化卡片的呈現需求，開發、部署與推廣的整體成本最低。
  **改變條件與備案：** 未來若規劃更複雜的落點分析圖表、跨科系比較表格時，LINE 的排版將不敷使用，此時會以建立 React (Next.js) Web 平台作為備案。

## 🛠️ 決策 2：基礎建設與後端技術選型
- **問題現況／需求**：
  專案需要一個能夠快速迭代部署、維護成本趨近於零，同時能夠存放大量結構化關聯資料（全台學校-系所-報名資訊）的後端與資料庫架構。
- **問題拆解方式**：
  獨立評估運算層 (API Server/Webhook Receiver) 與 儲存層 (Database)。
- **解方選項**：
  1. Python (FastAPI) + AWS EC2 虛擬機 + 傳統 MySQL。
  2. Go + Vercel Serverless + MongoDB (NoSQL)。
  3. Node.js (TypeScript) + Google Cloud Functions (2nd Gen) + Supabase (PostgreSQL)。
- **最終行動決策**：
  👉 **選擇選項 3 (TypeScript + GCP Functions + Supabase)**。
  **為何選它：** Supabase 提供強大的關聯式資料庫 (PostgreSQL) 支援，完美契合學校與系所間的一對多 (One-to-Many) 複雜關聯，並為日後向量檢索 (pgvector) 留下擴充空間。GCP Functions 2nd Gen 則在處理 LINE Webhook 的冷啟動時間與並發穩定度上表現優異。TypeScript 則保證了程式碼重構的安全性。
  **改變條件與備案：** 若未來 API 請求量大增導致 Serverless 費用高於預期，將把 Express 應用程式打包為 Docker，轉移至自建 VPS (如 DigitalOcean 或 GCP Compute Engine) 部署。

## 🕷️ 決策 3：爬取與結構化外部開放資料
- **問題現況／需求**：
  需要取得全台 140+ 所大學、數千個碩博士班的報名時程與官方簡章網址。但教育部或各校網站的 HTML 結構不一、表格混亂且常有動態載入，傳統 DOM 爬蟲維護堪憂。
- **問題拆解方式**：
  尋找一種能夠「理解非結構化或髒亂網頁」並直接輸出乾淨文本的現代化爬取方式。
- **解方選項**：
  1. 使用 Puppeteer / Cheerio，針對幾十所重點大學手刻 DOM 解析規則。
  2. 使用純 LLM (如 GPT-4) 直接讀取整包 HTML source code 進行資料提取。
  3. 導入 Firecrawl AI，將混亂的網頁預處理並展平為乾淨清楚的 Markdown，再餵給本地 Node.js 腳本進行邏輯截取。
- **最終行動決策**：
  👉 **選擇選項 3 (Firecrawl AI 爬蟲架構)**。
  **為何選它：** Firecrawl 能極大化地將髒亂的 HTML 表格（哪怕是巢狀結構）轉換成易讀的 Markdown。結合此預處理步驟加上我們在本地端寫的 Regex 腳本，資料清洗的成功率逼近 95%，且不需因為網站改版就頻繁維護 DOM selector。
  **備案：** 若 Firecrawl 失效或遭阻擋，我們已經實作了 `import_csv.ts`，能直接攝取教育部的官方 CSV 靜態名單，輔以人工或傳統腳本補齊缺少的網址。

## 🔍 決策 4：搜尋引擎與關鍵字別名 (Alias) 解析架構
- **問題現況／需求**：
  使用者的搜尋習慣大多為簡稱（例如：「台大國企」、「交大資工」），甚至中英文夾雜（例如：「NTU CS」）。直接在 DB `LIKE '%台大資工%'` 會找不到名為「國立臺灣大學資訊工程學系」的資料。
- **問題拆解方式**：
  探索能將「人類非正規口語實體」對應到資料庫正式 `school_id` 與 `program_id` 的技術。
- **解方選項**：
  1. 建立巨大的 JSON Mapping Object 寫死在程式碼中維護。
  2. 將所有系所介紹做向理化 (Vector Embedding)，引入向量語意搜尋。
  3. 在資料庫建立獨立的 `school_aliases` 與 `program_aliases` 關聯表，搭配「最長字串匹配演算法」與「不分大小寫處理」。
- **最終行動決策**：
  👉 **選擇選項 3 (RBAC 關聯表 + Longest Match Parsing)**。
  **為何選它：** 搜尋系所極度強調**精確度**，向量搜尋很容易因為「資工」與「資管」語意相近而推論錯誤。我們設計的 `keyword.ts` 演算法採用「先抽學校縮寫、再將剩餘字串比對系所縮寫」的兩段式過濾，能確保「台大政治」不會錯誤配對到「政治大學」，搭配大小寫忽略修復 (Case Insensitive)，穩定度最高。
  **備案：** 若未來縮寫變異太多難以窮舉，考慮掛載 LLM 進行即時實體提取 (Entity Extraction) 後再轉譯為 SQL 查詢。

## 🤖 決策 5：導入 AI 對話顧問與 RAG (檢索增強生成)
- **問題現況／需求**：
  搜尋模式只能服務「已經知道要找什麼」的人。對於「我想考文科，有什麼推薦？」的使用者，系統會失效。我們需要 AI 提供選校建議，但市面上的 LLM 直接回答極易發生「資訊幻覺」（推薦不存在的系所）。
- **問題拆解方式**：
  必須限制 LLM 只能基於 GradSearch 資料庫內部「真實存在的系所」給出建議，並妥善管理對話紀錄與 API 成本。
- **解方選項**：
  1. 直接使用 System Prompt，警告 LLM 不要說謊（防止幻覺成效極差）。
  2. 掛載外部工具 (Function/Tool Calling)，令 LLM 判斷用戶意圖後，由它呼叫我們的 DB Search API 再回答。
  3. 實作 LangChain/LlamaIndex 等重型 Agent 框架處理。
- **最終行動決策**：
  👉 **選擇選項 2 (Gemini-2.5-Flash + Function Calling + 對話次數管理)**。
  **為何選它：** `gemini-2.5-flash` 速度飛快且成本極低。我們利用 JSON Schema 強制 AI 回傳包含 `search_keywords` 的物件；這使得我們的 Node Server 能作為 Proxy 代理查詢資料庫，找到**確實存在**的系所後，再交給 AI 組合回答，保證零幻覺。此外，為避免無效廢話迴圈，在 Prompt 強制加入「最多詢問 2 次」的邊界條件限制。
  **改變條件：** 未來若互動流程更複雜（例如分析歷年錄取分數走勢），會考慮導入 LangGraph 這類具備狀態樹管理的 Agent 架構。

## 🛡️ 決策 6：搜尋失敗的防禦與資料庫自癒機制 (Auto-Healing)
- **問題現況／需求**：
  系統上線後必然會面臨兩種長尾錯誤：(1) 無法識別的新奇縮寫（導致搜不到）、(2) 學校官網默默改版導致原本的網址變成死連結 (404)。仰賴人工處理反饋 `( /bug )` 成本太高。
- **問題拆解方式**：
  設計一套機制，讓 /bug 訊息不只是紀錄，還能即時「自我分析與修復資料庫」，同時必須兼顧避免被惡意竄改（如駭客把網址改成釣魚網站）的絕對安全。
- **解方選項**：
  1. 簡單關鍵字觸發：若文字包含「網址錯誤」，直接把後面的 URL 寫進 DB。（零安全性）
  2. 全人工審核：使用者發送 `/bug` 後存入 GitHub Issue，開發人員每天巡邏手動下 SQL 解 Bug。
  3. **Defense in Depth**: LLM 意圖識別 + 擷取欄位 + Regex 安全白名單雙層防護。
- **最終行動決策**：
  👉 **選擇選項 3 (Gemini LLM 提取 + Code 網域白名單攔截)**。
  **為何選它：** 這是兼顧 UX 與 Security 的最佳解。遇到報錯時：
  1. 先派頂規邏輯模型 `gemini-2.5-pro` 理解抱怨文字，區分是 `ALIAS_ADD` 還是 `URL_UPDATE`。
  2. **安全閥：** 在真正寫入 supabase 前，由 `isValidAndSafeUrl()` 攔截。只放行結尾為 `.edu.tw` 等學術網址，若不符合一律阻擋並轉送至 GitHub Issue 由人工審核。
  這個決策使得系統能在短短幾秒內修正「台大中文網址錯誤」，而不會被惡意的「台大國企網址是色情網站」漏洞攻擊，達成自動運轉的堅韌資料庫體系。
